# Dynanotch input freeze and startup warning — 10 November 2026

## Conclusion
The evidence establishes an Accessibility-permission deletion immediately before the reported freeze, stale app-path lookups after cleanup, and a risky event-tap recovery policy. It does **not** establish a kernel/firmware crash, the owner of the stalled WindowServer connections, or the cause of the startup verification warning. No reproduction was attempted.

## Confirmed timeline (GMT)
- 19:20:22: Dynanotch PID 14889 starts; TCC attributes it to `/Applications/Dynanotch.app`, bundle ID `com.eduannnn.quickshell-notch.mac`.
- 19:21:11–19:21:18: WindowServer clears several clients' datagram buffers. The messages explicitly say `connectionIsUnresponsive: 0`; the client IDs have not been associated with Dynanotch. These messages precede the permission deletion and are not proof of its cause.
- 19:21:24: TCC reports failures resolving moved Dynanotch backup/build bundles. This is concrete evidence of stale paths after the earlier cleanup. There are 57 such failures across the captured interval; it is not evidence of a sustained runaway loop.
- 19:21:32.224: TCC receives `TCCAccessResetInternal`.
- 19:21:32.225: TCC publishes Delete for `kTCCServiceAccessibility`, identifier `com.eduannnn.quickshell-notch.mac`.
- 19:21:33.306: WindowServer checks Dynanotch access again. Selected preboot logging continues through 19:21:42; missing later logs cannot distinguish a hang from unflushed data after power-off.
- 19:23: system reboot recorded. User reports holding power to shut down, then seeing “Could not verify startup disk” and Recovery/startup disk choices before a successful subsequent boot.
- After reboot: Dynanotch is already running as PID 775. Investigation did not launch or terminate it.

## Code findings
- `Sources/NotchMac/MediaKeyService.swift:65`: filtering tap mask contains system-defined/media-key events (14), keyDown and keyUp; it does not subscribe to mouse buttons.
- Lines 58–61: a two-second main-run-loop timer checks Accessibility and tears down the tap if access is lost, otherwise re-enables a disabled tap. This is eventual handling, not an immediate revocation guarantee.
- Lines 85–89: timeout and user-disable callbacks immediately re-enable the tap when started, without a fresh permission check, backoff, or timeout limit. This is a confirmed recovery weakness; no captured message proves it executed during the freeze.
- `Sources/NotchMac/NotchModel.swift:217–225`: tap actions perform synchronous Core Audio refresh/set calls. A stalled service could delay the filtering callback. No stack capture from the incident exists to show that happened.
- `NotchPanelController.swift`: mouse global monitors observe only; the local pointer monitor returns events unchanged. The transparent panel is bounded to the notch canvas, with pointer-based click-through. Code review alone cannot exclude an unexpected window-state issue.

## Startup status and limits
Read-only `diskutil info /` reports the current Macintosh HD APFS snapshot as mounted read-only and sealed, SMART status Verified, with ample container free space. SIP and authenticated root are enabled. These are current status checks, **not** an exhaustive filesystem, SSD, firmware, or boot-policy validation.

No new panic or matching WindowServer/Dynanotch crash report was found in the accessible system/user DiagnosticReports and Retired entries inspected. The recent analytics files are not panic reports. Absence of a panic report is compatible with a forced power-off and does not rule out a severe hang.

The preboot verification screen is user-reported and is not explained by the captured successful-boot logs. No causal link from the userspace input filter to that warning has been established. No further boot/security changes or live disk checks were attempted.

## Recommended next action
Quit Dynanotch before any further permission removal/re-add operation; do not reproduce this live with the current input filter. Before another test, make the tap fail open on timeout/user-disable, avoid automatic immediate re-enabling, move blocking device work outside the synchronous callback, and add bounded diagnostics for tap state, permission transitions and callback durations. Validate without revoking permissions on the primary desktop first.

Do not reset the full TCC database or change boot security. If the startup warning recurs, preserve its photo/exact text and use Apple's Recovery guidance; do not treat the successful reboot as proof that storage has been completely checked.
